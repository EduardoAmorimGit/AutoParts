# AGENTS.md

Spring Boot 4.1.1 REST API (Java 17, Maven). Early-stage. Product catalog: Flyway migration + `products` table, JPA entity/repository, `ProductService` (CRUD + DTOs + validation) and REST API `/api/products` (`ProductController` + `@RestControllerAdvice`). Reads are public; writes require an ADMIN JWT. `GET /api/products` is paginated/sorted (Spring Data `Pageable`, default size 20, max 100, default sort `id,asc`) and returns the `common/PageResponse` envelope (`content`, `page`, `size`, `totalElements`, `totalPages`, `first`, `last`). SKUs are normalized (trim + uppercase, `Locale.ROOT`) before persistence and duplicate checks.

- Freeze 8: vehicle plate lookup (`/api/vehicles/lookup`) via Simples API + product/vehicle compatibility (N:N). The external provider is isolated under `integration/vehicle` behind the `VehicleLookupProvider` interface; only `SimplesApiVehicleLookupProvider` knows the provider URL/headers/JSON. `RestClient` (Spring 7) is used, no new dependency. The API key comes from `simples-api.api-key=${SIMPLES_API_KEY:}`; when blank the provider bean is absent and `/api/vehicles/lookup` returns 503. `Vehicle` is keyed by a normalized (uppercase, every non-alphanumeric character removed) unique `plate`; lookup reuses an existing plate without calling the provider again. The stored plate is always the normalized *requested* plate, never the one echoed by the provider. Provider JSON is parsed as `tools.jackson.databind.JsonNode` (Jackson 3 has no `tools.jackson` `@JsonProperty`), and missing/null fields are kept null. Compatibility moved to vehicle specs and fitments (Delivery 3a below).
- Delivery 3a (vehicle fitments, package `compatibility`): compatibility is per vehicle *spec* ("ficha": brand, model, optional version/engine, fuel, model-year range, oil capacity), never per plate and never inferred. Flow: plate -> `Vehicle` (provider data) -> `SpecResolutionService` (existing `vehicle_spec_assignments` row, else an admin alias in `vehicle_spec_aliases` keyed by the provider-data signature, else the conservative `SpecMatcher`; ambiguity = no match) -> `product_fitments` with status `VALIDATED` -> active products. `GET /api/vehicles/{id}/products` (public) returns `{status: RESOLVED|PENDING, spec, products}`. Fitments come from CSV imports of real catalogs (`POST /api/admin/fitments/import`, multipart `file`, `dryRun`; columns sku, marca, modelo, versao, motor, combustivel, ano_inicio, ano_fim, capacidade_oleo_litros, fonte, observacao; `fonte` is mandatory) and start as `IMPORTED`; admins review them (`POST /api/admin/fitments/review`) or add validated ones by hand (`POST /api/admin/fitments`). Other admin endpoints: `/api/admin/vehicle-specs` CRUD, `GET /api/admin/vehicles/pending` (vehicles without a spec), `PUT /api/admin/vehicles/{id}/spec` (manual assignment + alias), `POST /api/admin/vehicles/rematch`. Names are normalized by `VehicleNames` (uppercase, no accents, brand aliases such as VW/GM, `I/` import prefix, brand stripped from the model). Never let an AI or heuristic invent fitments: data must come from a cited source and be validated. The legacy per-plate `product_vehicle` table was dropped in V8.
- Delivery 3b (catalog admin, package `product`): products have `type` (`ProductType`: ENGINE_OIL, OIL_FILTER, AIR_FILTER, FUEL_FILTER, CABIN_FILTER, OTHER; drives behaviour), optional `category` (`Category`, unique slug; public `GET /api/categories`, admin CRUD under `/api/admin/categories`; deleting a category clears it from products), `viscosity` (normalized, e.g. 5W30), `oilSpecification`, `packageVolumeLiters` and ordered https `imageUrls` (`product_images`; URLs only, upload not decided). `ProductRequest` keeps a 7-argument convenience constructor. `GET /api/products` filters by `type`, `categoryId`, `q` (name/SKU/brand) and hides inactive products unless an ADMIN passes `includeInactive=true`; `GET /api/products/{id}` returns 404 for inactive products to non-admins. `POST /api/admin/products/import` (multipart `file`, `dryRun`) upserts by SKU; rows without price are skipped with a warning, blank cells keep current values, each row is fully validated before it touches the entity, and a bare "Oleo" type is rejected as ambiguous. The customer response of `GET /api/vehicles/{id}/products` also has `kits`: `OilChangeKitBuilder` combines fitted (validated) engine oil units covering the spec oil capacity plus one fitted oil filter, cheapest total with enough stock.
- Delivery 4 (cart and checkout; packages `customer`, `store`, `cart`, `order`): customers keep up to 10 addresses (`/api/me/addresses`, digits-only CEP/phone) and only addresses inside `DeliveryArea` are accepted (`delivery.cep-ranges`, default 20000000-23799999 + city Rio de Janeiro/RJ; 422 otherwise, re-checked at checkout). District, city and state are taken from the CEP via `integration/cep/CepLookupProvider` (ViaCEP, `cep-lookup.*`; called outside DB transactions, unknown CEP 422, provider down 503; the customer's district is kept only when the CEP has none), so customers cannot pick a cheaper district. Tests stub it with `support/CepLookupTestConfig` (`@Import`). Delivery fees (package `delivery`, V12, replaced the old fixed `store_settings` fee): admins group districts into `delivery_regions` (`/api/admin/delivery-regions` CRUD; a district, compared by `DistrictKey` without accents/case, belongs to at most one region; inactive regions and regions with a NULL fee serve nobody; V13 seeds the Rio regions Centro, Zona Sul, Zona Norte, Barra e Jacarepaguá and Zona Oeste with the official bairros and NULL fees, so integration tests that create their own regions first run `DELETE FROM delivery_regions` (rolled back); `GET /api/admin/delivery-regions/uncovered-districts` lists districts of saved addresses with no active region). Address responses carry `delivery {region, fee}` (null = not served); `GET /api/cart?addressId=` prices delivery; checkout refuses unserved districts with 422 and snapshots `delivery_region` in the order. The cart (`/api/cart`, `PUT /api/cart/items/{productId}` with quantity 0-99, 0 removes) stores product + quantity only and recomputes prices live. `POST /api/checkout` requires header `Idempotency-Key` (8-64 chars; same key returns the same order), locks the products with `ProductRepository.findAllForUpdate` (sorted ids, no deadlocks), decrements stock (reservation), snapshots prices/names/address into `orders`/`order_items` and clears the cart. The JPA entity name of `order/Order` is `CustomerOrder` (ORDER is a JPQL keyword). Orders start `AWAITING_PAYMENT`; `OrderStatus.canMoveTo` holds the state machine; customer cancel (`POST /api/orders/{id}/cancel`) only while awaiting payment, and `OrderExpiryJob` (`orders.payment-timeout`, default 30m; disabled in tests via `orders.expiry-job.enabled=false`) cancels overdue orders; cancellation returns stock. Customers only see their own orders (others read as 404); admins use `GET /api/admin/orders[?status=]` and `/api/admin/orders/{id}`. Tests that touch cart/orders need real users (FKs): register via `AuthService` and use `TestAuth.customer(userId)`.
- Delivery 5 (payments, package `payment`): Mercado Pago Checkout API over REST (`payment/gateway/MercadoPagoGateway`, no SDK) behind the `PaymentGateway` port; the bean exists only when `MERCADOPAGO_ACCESS_TOKEN` is set (otherwise payment endpoints answer 503). Pix and credit card only (online debit postponed by the product owner; `payments.max-installments`, default 1). `PaymentService` never calls the provider inside a DB transaction: (1) `TransactionTemplate` locks the order (`OrderService.lockForPayment`) and records a `payments` row with a UUID `idempotency_key` (sent as `X-Idempotency-Key`), (2) calls the provider, (3) applies the result. `external_reference` = `autoparts-payment-{paymentId}` links provider payments back. A Pix expires >= 31 min (provider minimum 30) and pushes the order deadline (`extendPaymentDue`) to Pix expiry + 5 min; an open Pix is reused. Card tokens come from the frontend Card Payment Brick (card data never reaches the server); `three_d_secure_mode=optional`, challenges are returned to the client and `POST /api/orders/{o}/payments/{p}/sync` re-reads the payment. Webhook `POST /api/payments/webhooks/mercadopago` (public) validates `x-signature` with `WebhookSignatureVerifier` (manifest `id:<data.id>;request-id:<x-request-id>;ts:<ts>;`, HMAC-SHA256 with `MERCADOPAGO_WEBHOOK_SECRET`, as in the official SDK) and then fetches the payment (body not trusted). Approval pays the order only if the amount matches and the order still awaits payment; otherwise the payment is refunded automatically and flagged (`needs_attention`, admin `GET /api/admin/payments/attention`); chargebacks are flagged. Public `GET /api/payments/config` returns the public key. Tests use `payment/FakePaymentGateway` (`@Import(FakePaymentGateway.Config.class)`) and `MockRestServiceServer` for the real client. Not yet verified against the Mercado Pago sandbox (pending test credentials): Pix `date_of_expiration` format and simulating an approved Pix.

## Commands
Use the Maven wrapper (Maven 3.10.0), not a system `mvn`.
- Start local DB (for running the app): `docker compose up -d` (Postgres 17 on `localhost:5433`); stop: `docker compose down`
- Tests need only a running Docker daemon (Testcontainers starts a throwaway Postgres 17); CI runs `./mvnw -B verify` (`.github/workflows/ci.yml`).
- Build: `.\mvnw.cmd clean package` (Windows) / `./mvnw clean package`
- Run: `.\mvnw.cmd spring-boot:run`
- All tests: `.\mvnw.cmd test`
- Single test: `.\mvnw.cmd test -Dtest=AutopartsMavenApplicationTests`
- Compile only: `.\mvnw.cmd compile`

## Gotchas
- Base package is `com.autoparts_maven.autoparts_maven` (underscores, not dots) and lives under `src/main/java/com/autoparts_maven/autoparts_maven/`. Match it exactly for new code.
- `application.properties` uses `DB_URL` (default `jdbc:postgresql://localhost:5433/autoparts`), `DB_USERNAME` and `DB_PASSWORD` (both default to `autoparts`, matching `docker-compose.yml`). Integration tests use the `test` profile (`src/test/resources/application-test.properties` + `@ActiveProfiles("test")`), whose datasource is the Testcontainers JDBC URL `jdbc:tc:postgresql:17-alpine:///autoparts?TC_DAEMON=true` (override with `TEST_DB_URL`). Only `org.testcontainers:testcontainers-postgresql` (test scope) is needed; `spring-boot-testcontainers` is not used.
- Host port **5432 is occupied by a native PostgreSQL 18 Windows service** (`postgresql-x64-18`). The Docker Postgres is intentionally published on **5433**; do not move it back to 5432.
- Schema is managed by Flyway through `spring-boot-starter-flyway`. Plain `flyway-core` will NOT run migrations in Spring Boot 4 (autoconfiguration is in the starter). Migrations live in `src/main/resources/db/migration` (naming `V<n>__desc.sql`). JPA runs with `ddl-auto=validate`, so entities must match the migrated schema.
- PostgreSQL is the only runtime datasource. Tests that boot the context need Docker running.
- Lombok is wired through `maven-compiler-plugin` `annotationProcessorPaths` (both compile and test-compile). Keep that config if editing plugin settings.
- This is Spring Boot 4: web uses `spring-boot-starter-webmvc` and test starters are per-module (`spring-boot-starter-*-test`), not the older `spring-boot-starter-web` / aggregate `spring-boot-starter-test`. In Boot 4 `@AutoConfigureMockMvc` lives in `org.springframework.boot.webmvc.test.autoconfigure`.
- `spring-boot-starter-security` is on the classpath with `config/SecurityConfig` (Spring Security 7 lambda DSL; first matching rule wins). Public: `/actuator/health`, `POST /api/vehicles/lookup`, `GET /api/vehicles/*/products`, `GET /api/products/**`. Everything else under `/api/products/**`, `/api/vehicles/**` (including `GET /api/vehicles/{id}`, which exposes the plate) and `/api/admin/**` requires the `ADMIN` role; other paths (`/api/me/**`) require any authenticated user.
- Delivery 2 (identity, package `identity`): authentication is a stateless OAuth2 resource server with self-issued HS256 JWTs (`config/JwtConfig`, `auth.jwt.*`, key from `JWT_SECRET`, min 32 bytes; random key in dev when blank, startup fails under `prod`). HTTP Basic and the in-memory user are gone. Access token (15 min): `sub` = user id, `roles` claim = [role] (no e-mail/name in claims). Refresh token (30 days): opaque random value, only its SHA-256 stored in `refresh_tokens`; `/refresh` rotates it under a row lock, and reuse of a revoked token revokes all of that user's sessions. Endpoints: `POST /api/auth/register` (always CUSTOMER), `/login`, `/refresh`, `/logout` (public; register/login rate-limited per IP via `authRateLimiter`), `GET /api/me`, `PUT /api/me/password` (revokes all refresh tokens), `GET /api/admin/users` (ADMIN). Login failures share one message (no account enumeration; unknown e-mails still run a BCrypt check). E-mails are stored trimmed + lowercase. `AdminBootstrap` creates the first ADMIN from `ADMIN_EMAIL`/`ADMIN_PASSWORD` (dev defaults `admin@autoparts.local`/`admin`) only when no admin exists; under `prod` a blank/default password stops startup. Password reset is not implemented yet (needs an e-mail provider decision). Tests authenticate with `support/TestAuth.admin()`/`customer()` (spring-security-test `jwt()`), and `identity/AuthControllerTest` covers the real token flow.
- Rate limiting: `common/ratelimit/FixedWindowRateLimiter` (in-memory, per instance) with beans `lookupRateLimiter` and `authRateLimiter` in `config/RateLimitConfig`; inject them with `@Qualifier`. `RateLimitExceededException` → 429 + `Retry-After` in `GlobalExceptionHandler`. 401/403 return `ProblemDetail` JSON via `ProblemDetailAuthenticationEntryPoint`/`ProblemDetailAccessDeniedHandler`. `DispatcherType.ERROR` is permitted so error responses are not masked as 401. Controller tests authenticate with `support/TestAuth` (JWT) or `@WithMockUser`.
- Error handling: `common/web/GlobalExceptionHandler` (`@Order(LOWEST_PRECEDENCE)`) maps framework/persistence errors to `ProblemDetail` (`application/problem+json`): bad path variable, malformed body, invalid sort, missing parameter, unsupported method (with `Allow`) or media type, unknown path, `DataIntegrityViolationException`/optimistic lock (409) and an `Exception` fallback (500, logged). Module advices (`product/ProductExceptionHandler`, `vehicle/VehicleExceptionHandler`) are `@Order(0)` so they win over the fallback; keep that ordering for new module advices. `Product` has `@Version`: responses carry `version` and an `ETag`; `PUT` honours an optional `If-Match` (stale → 412). A `PUT` without `active` keeps the current status. Timestamps use Hibernate `@CreationTimestamp`/`@UpdateTimestamp`. `GET /api/products` returns the `common/PageResponse` envelope. SKUs are normalized (trim + uppercase, `Locale.ROOT`) in `ProductService` before persistence and duplicate checks.
- Vehicle domain: `vehicle/VehicleService.lookupByPlate` (intentionally not `@Transactional`, so the provider call holds no DB connection) normalizes/validates the plate, reuses an existing `Vehicle` or, after the `lookupRateLimiter` (per-IP, `vehicle-lookup.rate-limit.*`; cache hits are free), fetches from the provider and persists it (a concurrent insert of the same plate is resolved by re-reading) (only when `VehicleLookupProvider` is configured; otherwise `VehicleLookupDisabledException` → 503). Provider failures map to `ProblemDetail`: 401/403 → 502, 429 → 429, 422 → 502, 503/unreachable → 503, unknown → 502, generic `RestClientException` (communication/conversion) → 502. The provider never exposes upstream messages, bodies or headers to clients, and logs only technical info (status code / exception class), never the plate, API key, headers or payloads. `Vehicle` persistence stores the plate (indirect personal data, LGPD) plus technical fields solely to link a vehicle to compatible products and avoid re-querying the provider; no owner/CPF/address or provider `city`/`state` are stored, and `color` was dropped from persistence (V4) and from `VehicleResponse` (no compatibility purpose). There is no automated retention/purge job yet. Not-found errors for a plate never echo the plate. Tests use `VehicleLookupTestConfig` (`@Import`) to stub the provider; the real provider is never called in tests.

## Conventions
- `HELP.md` is gitignored and is stock Spring Initializr boilerplate; ignore it.
- `.gitattributes` pins `mvnw` to LF and `*.cmd` to CRLF; don't reformat those line endings.
- `.env*` files are gitignored. Never commit secrets; rely on env vars.
- Default branch is `main`.
